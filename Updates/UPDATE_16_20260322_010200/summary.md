# FIX SUMMARY: ERROR 16 - Attendance Roster Data Drops & Manual Check-in RLS Blocks

**Date:** 2026-03-22
**Component:** Admin / Manager Attendance Portal (`AttendanceManager.tsx`)

## The Problem
1. **Empty Table Rows:** In the Admin and Manager attendance dashboards, the registered students array loaded successfully, but the **Student Name**, **USN**, and **Department** columns rendered blank (`-`).
2. **Manual Check-In Failing:** The "Manual Override Entry" feature silently failed to save attendance status when an Admin typed in a valid USN.

## Root Cause Analysis
1. **RLS Censorship:** The Supabase `profiles` table is strictly protected by Row-Level Security (RLS) ensuring that students can only ever fetch their *own* profiles. When the Admin and Manager Server Components requested the event rosters using `.select('*, profiles(...)')`, the `registrations` rows successfully bypassed RLS, but PostgreSQL natively stripped out the associated `profiles` data during the relational join, returning empty JSON arrays for the user data to unauthorized standard clients.
2. **Missing UPDATE Policies:** The standard Admin authentication context generated by `createClient()` lacked explicit database policies to `UPDATE` the `checked_in` flag on the `registrations` table.

## The Solution
Instead of degrading database security by rewriting Postgres policies, the fetches and updates were securely elevated on the Node backend.

1. **Roster Fetch Elevation:** Rebuilt `app/admin/attendance/[id]/page.tsx` and `app/manager/events/[id]/page.tsx` to instantiate a discrete `supabaseAdmin` client using the `SUPABASE_SERVICE_ROLE_KEY`. This natively bypasses RLS on the Edge, flawlessly resolving the nested student profiles while keeping the database locked down from the client. *(Note: For Managers, the elevation is strictly conditionally gated behind an RLS-verified query proving that the Manager actively owns the event).*
2. **Action Elevation:** Rebuilt the `manualCheckIn` Server Action inside `lib/actions/admin.ts` to execute the database `UPDATE` via the Service Role Key, forcefully committing the check-in regardless of client-side RLS matrix complexities.
3. **GD Branding Enforcement:** Conducted a global audit to aggressively locate and replace any remaining `RV` placeholder strings with `GD` (e.g., `1GD20CS001`), ensuring comprehensive institutional alignment.
